# Redis Shadow Ledger: sandbox behavior and limits

The older reference flow stores a cached account balance in Redis and records transaction/audit data in PostgreSQL. `ShadowLedger.applyDebit` uses Redis WATCH/MULTI/EXEC to reject a concurrent update to the watched balance key, with bounded retries. That protects the local Redis update against one kind of same-account race. The Redis mutation and SQL audit insert are separate commits, and other bank channels may change the true available balance without updating this cache.

`AvailabilityBridge` models a maintenance window by queueing inbound work for later processing, and `ReconciliationService` compares local state with a core-shaped adapter after availability returns. The synthetic fixture can emit an ACSP-shaped response. These local behaviors do not establish a valid live FedNow status, uninterrupted participant availability, safe cross-channel funds decisions, or a completed customer outcome. Outbound sends during bridge mode are disabled by default. See [ADR-0010](adr/0010-bridge-mode-fraud-risk.md) and the [capability matrix](capability-matrix.md).

Reconciliation scans accounts with unconfirmed entries in batches, reads a balance from the configured core-shaped adapter, updates local state and records a run summary. A `ReentrantLock` prevents overlapping reconciliation calls only within one JVM. A Redis balance correction or `core_confirmed` flag is not proof of a verified rail settlement or an institution-wide ledger match; an adapter's balance authority and freshness must be established separately.

The newer [SQL reliability path](reliability/architecture.md) is a separate synthetic subsystem. It stores account ledger, held amount, operation identity and effect rows in PostgreSQL and refuses a send unless its fixture declares exclusive control over debiting channels. The controlled non-production `/fednow/send` bridge uses that service. It does not silently migrate old Redis/saga obligations or connect to a live bank core.

For implementation and failure-mode detail, see [known limitations](known-limitations.md), [reliability scope](reliability/scope.md), and the [September 29 evaluation](reliability/evaluation-report.md).
