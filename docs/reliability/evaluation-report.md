# Synthetic payment reliability evaluation — candidate 2026-09-28

**Question.** Under the tested synthetic faults, does the reference path preserve a durable payment obligation, avoid duplicate or premature financial effects, and expose evidence needed to reconcile an uncertain outcome? Does the same external oracle work with another target? This report describes observed behavior in controlled fixtures; it is not FedNow certification, vendor validation, a bank deployment, or an economic-impact estimate.

**Source under test.** `84480178efa8203edc1c21e76903e9bb060298ad` on `development/reliability-reference`, clean working tree when the final evaluation began. The source ZIP and per-file SHA-256 manifest are in [the evidence bundle](evidence/candidate-2026-09-28/). This report and claim corrections are a later documentation-only commit. The baseline was clean `c7e5acb6142d180b756a67afd92e3cf5291d99a1`. Its one passing defect-characterization test observed a received synthetic request, client timeout, fabricated `RJCT/NARR`, and compensation. That test used mocks and is not a ledger or remote-effect oracle; a numerical baseline-to-candidate failure-rate comparison is therefore **not available**.

## Method and observed results

The final command was `python3 scripts/evaluate.py --integration --negative-control --external` with JDK 17, Maven 3.9.16, Python 3.9.6, Docker Engine 29.7.2, PostgreSQL 16, Redis 7 and RabbitMQ 3 on macOS 27 / Apple Silicon. The dependency-resolution step passed. The selected control suite passed **48/48**, and selected integration tests passed **63/63**, with zero skips or errors. Separate full runs on the same source passed **616/616 default tests** and **206/206 integration tests**. Their full console logs are archived. No result from a skipped dependency is counted as a pass.

The external [scenario manifest](../../harness/scenarios-v1.json) ran the same eight cases with the same oracle against (1) OpenFedNow's synchronous SQL-reservation fixture, (2) its asynchronous core-acknowledgment/lookup fixture, and (3) a separate Python/SQLite reference target that imports no OpenFedNow domain code. Each configuration passed **8/8** applicable cases: S01–S03, S06–S07, S14, S16–S17. The oracle compared payment state, operation-keyed HOLD/POST/RELEASE rows, expected versus observed account ledger/held amounts, and the independent rail simulator's status and submission count. The accepted lost-response case S02 ended `SETTLED`, with one remote submit, one HOLD, one POST, ledger 90,000 and held 0 minor units from an initial 100,000 and a 10,000 payment. The lost-rejection case S03 ended `REJECTED`, with one remote submit, one HOLD, one RELEASE, ledger 100,000 and held 0. S06's deterministic two-request barrier had one remote submission on each target. S14 refused a send when another channel could debit outside the declared reservation authority. S17 intentionally corrupted a local success observation; the external effect comparison detected the inconsistency. These are fixed schedules and author-built fixtures, not a stress or probability study.

S05 ran separately against the Java target: the process was killed with `SIGKILL` **after the simulator recorded the remote effect and before the local result was persisted**. PostgreSQL still showed `SUBMITTING` and a 10,000-unit hold after restart. An inquiry later produced one POST and `SETTLED`; the simulator recorded one submission. This was one deterministic kill boundary. The test fixture made inquiry due; the roughly nine seconds between archived pre-inquiry and final timestamps is a local run duration, **not** a FedNow inquiry timing claim. The normal profile waits 30 synthetic seconds before inquiry. Unknown-state duration distributions and throughput were not instrumented; no capacity claim follows from this run.

Six isolated source mutations were detected by exactly one expected assertion failure each, with no build errors, harness timeouts or skipped tests: bypass atomic claim, release a hold on unknown outcome, ignore a duplicate event, omit possible-send intent, force uncertainty to rejection, and bypass the existing screening guard. The mutation results are in `results.json`, with per-test JUnit XML and console logs. These controls establish that those particular assertions respond to those particular defects; they do not measure general defect-detection sensitivity.

## Coverage and failures

[The source-to-scenario register](requirements.csv) gives each S01–S18 result and limit. S04, S08–S13 and S15–S16 have Java-only or partial coverage; S05 is a separate restart experiment; S18 is the aggregate portability experiment. In particular, the external runner does **not** exercise every fault class or every scenario. A full crash-window matrix around broker/outbox commits, cross-process inquiry-worker failover, a durable return lifecycle, core-outage and reservation-expiration matrix, and live inquiry eligibility remain open. The reference slice publishes no broker event and makes no outbox guarantee. The separate target demonstrates reuse by an author-built implementation, not independent bank adoption. Driver setup required two small Python processes and the documented Java/PostgreSQL configuration; adapter engineering time and resource consumption were not separately measured.

During development, the first full PostgreSQL integration run had two failed migration/table-count assertions after additive V9–V10 tables were introduced. The assertions were corrected and the 204-test full run passed. The first external run failed five scenarios because the simulator did not parse Java's chunked request body; the parser was fixed and subsequent eight-case runs passed on all three targets. These failures are development results, not omitted trials of the final source. The final clean-source run reports zero failed applicable cases. Current stacked PRs target development branches, while GitHub CI workflows trigger on PRs to `main`; [the archived CI record](evidence/candidate-2026-09-28/ci-records.json) shows no checks for those PRs. Local tests are not a substitute for a green main-targeted CI run.

The public [FedNow Operating Procedures v3.6](https://www.frbservices.org/resources/rules-regulations/operating-circulars/) informed the settlement/posting distinction and the decision not to infer rejection from a missing response. The 30-second wait, 15-second lease and three-inquiry escalation are synthetic engineering settings. Restricted FedNow message/transport/security specifications, institutional core contracts and vendor environments were unavailable; no live pacs.028 mapping, authenticated live status, certified rail connection or vendor behavior was tested. The adjacent cycle-day/calendar-day inquiry language remains unresolved for a live adapter.

## Reproduce and verify

The source snapshot does not include this later report or evidence bundle. The bundle excludes SQLite runtime databases because the JSON traces already preserve independent simulator effects and the databases were transient process artifacts. All account and payment identifiers are synthetic. Review [the architecture](architecture.md) and [scope](scope.md) before reusing results or connecting another adapter.
