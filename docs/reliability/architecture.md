# Synthetic reliability reference architecture

This decision applies to `/reference/v1/payments` and, only when explicitly enabled outside the production profile, the `/fednow/send` synthetic reliability bridge. The older router remains a separate sandbox demonstration. PostgreSQL is authoritative for synthetic account ledger balances, held amounts, scoped payment ownership, attempt intent, status events, and financial effects. Redis is not consulted for reference outbound claims or balances. An account is eligible only when its synthetic core fixture declares exclusive control over all debiting channels; otherwise the send is refused. The older Redis/SQL split route and return route are disabled by default at the gateway. The bridge delegates the existing send entry point to `ReliablePaymentService` and returns its operation view; it never calls the legacy router or a vendor-shaped core adapter.

## State and effect boundaries

`CORE_PENDING` (async fixture only) → `RESERVED` → `SUBMITTING` → `OUTCOME_UNKNOWN` → `SETTLED` or `REJECTED`. A correlated final synthetic status may also advance directly from `SUBMITTING`. A missing, malformed, unauthenticated, conflicting or untraceable status leaves the payment pending or in `INVESTIGATION`. `SETTLED` is service settlement; `postingStatus` is separately observed receiver posting. Posting never changes the sender's settlement or money effects.

The application inserts a unique `(institution, OUTBOUND, FEDNOW, business key)` operation and its `HOLD` in one SQL transaction. The amount uses exact USD minor units. A same-key/same-financial-payload request retrieves the existing operation; changed amount, payee, account or other fingerprinted field conflicts. Transaction and message identifiers are also scoped unique. The attempt ID and `SUBMITTING` transition commit before the external call. A process death after this commit is ambiguous even if it occurred before bytes left the process. Recovery may inquire but never resubmit a `SUBMITTING` or `OUTCOME_UNKNOWN` record. A `RESERVED` record has not crossed the possible-send boundary and a compare-and-set worker may dispatch it once. This is a conservative synthetic design; a real adapter would need a verified transport/effect boundary.

`HOLD`, `POST` and `RELEASE` have unique `(operation_id,effect_type)` identities. An account update and effect row commit together with the final state. Settlement posts the held amount by reducing both ledger and held balances; authoritative synthetic rejection releases held funds without reducing ledger. If any update fails, the SQL transaction rolls back; no final state or effect row is recorded. A confirmed settlement is never undone by locally restoring a balance. Returns are separate operations and are **not** implemented in this reference slice. The legacy return HTTP client makes one attempt and propagates uncertainty, while its gateway endpoint stays disabled by default.

Two author-built core fixtures exercise different sequencing. `SYNC` provides an atomic SQL reservation before dispatch. `ASYNC` records a hold and `CORE_PENDING` plus an acknowledgment record, with no rail send until explicit synthetic core acknowledgment/lookup. If the synthetic core is unavailable, a new send is refused before a hold and a pending asynchronous acknowledgment remains pending. After availability returns and the fixture acknowledges, the same compare-and-set dispatch boundary applies. These fixtures demonstrate two integration shapes, not FIS/Fiserv/Jack Henry capability or cross-channel correctness in a real bank.

The rail simulator is a separate Python process backed by SQLite. It records a `REMOTE_EFFECT` before optionally dropping the response or waiting at a barrier. The Java target sees only HTTP response/inquiry observations. This JSON protocol is deliberately not a FedNow wire protocol. The source label `SYNTHETIC_RAIL` is trusted only inside this controlled local test. Restricted service message and transport specifications, participant signing, and authenticated live status are unavailable. No live pacs.028 adapter is implemented.

## Inquiry and investigation

The synthetic rail profile waits 30 seconds after possible send before inquiry. The worker polls every 5 seconds, claims at most 20 due records, and uses a 15-second lease token; an expired or replaced lease cannot apply a result. A missing result is not a rejection. Three untraceable/failing inquiries or a synthetic 24-hour age limit move the record to `INVESTIGATION` with the hold intact. These values are engineering test settings, **not FedNow timing limits**. The fixture API can make a query due immediately for deterministic tests. The payment view records age, inquiry count, last inquiry and next action time. A two-JVM test verifies lease contention, expiration and stale-worker fencing. Operations can list unresolved records and request a review; review records authenticated actor, reason, prior/resulting state and evidence reference. A review can obtain a fresh simulator observation; the operator cannot enter a settlement status.

FedNow Operating Procedures v3.6 §15(e) distinguishes a FedNow service settlement status from a participant posting status and describes pacs.028 inquiry. Section 15(f) warns against inquiry while processing is underway. The public text uses cycle-day and calendar-day language in adjacent inquiry provisions; that interpretation is **not resolved** here for live use. The official [operating procedures index](https://www.frbservices.org/resources/rules-regulations/operating-circulars/) listed v3.6 effective April 28, 2026 when reviewed September 28. [FedNow DevRel](https://www.frbservices.org/resources/financial-services/fednow-service-resources/fednow-devrel/) holds credentialed technical materials needed for a live mapping.

## Capability contract and default posture

The [versioned adapter capability contract](adapter-capabilities-v1.md) conservatively classifies the existing FIS-, Fiserv- and Jack Henry-shaped adapters. An institution-facing send adapter would need to declare and test: balance source and freshness, all-channel enforceable reservation, reservation expiry/lookup, posting identity and idempotence, reversal identity and idempotence, operation lookup after lost acknowledgments, and deduplication scope. `ledgerMinor` is booked balance; `heldMinor` is unavailable reservation; synthetic available balance is `ledgerMinor - heldMinor`. Exact cents and USD are required; fractional cents are refused. A cached Redis balance, a one-time vendor balance read, or a reservation unknown to other channels does not satisfy this contract. `exclusiveControl=false`, a missing synthetic account, unavailable simulator, or unsupported currency disables the reference send. No STIP/card network is implemented.

The schema is additive at V9–V12. Historical `saga_state` unknowns are not migrated to new outcomes. A deployment must investigate those separately; this reference subsystem cannot infer their rail effects. Event publication from the older code is unchanged; the reference slice makes no broker-delivery claim. A transactional outbox and duplicate consumer tests remain necessary before publishing reference payment events. An outbox would not remove the post-send/pre-ack rail uncertainty.
